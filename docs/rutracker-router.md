# RuTracker на роутере

RuTracker состоит из трёх согласованных частей: выборочного DNS, перехвата TCP к служебному IPv4-адресу и локального Rust-прокси. Их запуском, проверкой и остановкой управляет [S99r2o](../router/S99r2o). Значения по умолчанию: sentinel `203.0.113.171`, порт прокси `1445`, включение `R2O_RT_PROXY=1`.

## Архитектура и платформы

| Платформа | DNS | Перехват HTTPS |
| --- | --- | --- |
| Keenetic с Entware | Штатный NDM: `ip host` и маршрут DNS для выбранного домена на отдельный dnsmasq `127.0.0.1:5354` | iptables: собственные цепи `R2O_RT_PRE` и `R2O_RT_OUT` в `nat` |
| OpenWrt с fw3 | Штатные UCI и dnsmasq; списки `address` и `server` для выбранных доменов | iptables, те же собственные цепи |
| OpenWrt с fw4 | Штатные UCI и dnsmasq; те же выборочные настройки | nftables: собственная IPv4-таблица `ip r2o_rt` |

Клиент, использующий DNS роутера, получает sentinel для выбранного имени. TCP-соединение к `sentinel:443` перехватывается в `PREROUTING` для клиентского трафика или в `OUTPUT` для трафика самого роутера и направляется в локальный прокси. Прокси передаёт клиентский TLS через HTTPS CONNECT; прямой резервный путь ограничен правилами runtime. Исходящие сокеты используют настроенную метку `MARK`, чтобы собственный трафик не попадал в повторный перехват. При нулевой метке firewall не добавляет правило обхода по mark=0.

DNS и firewall реализованы отдельными адаптерами:

- [r2o-rt-dns.sh](../router/r2o-rt-dns.sh): `apply`, `status`, `clear`.
- [r2o-rt-firewall.sh](../router/r2o-rt-firewall.sh): `apply`, `status`, `stop`.
- [rt_proxy.rs](../crates/r2o-telegram/src/rt_proxy.rs): Rust runtime.

### Выборочный DNS

Штатный список: `rutracker.org`, `www.rutracker.org`, `rutracker.wiki`, `api.rutracker.cc`, `rep.rutracker.cc`, `static.rutracker.cc`. В dnsmasq используются пары `address=/домен/sentinel` и `local=/домен/`; на OpenWrt второй параметр представлен UCI-списком `server=/домен/`. Область правил соответствует домену и его поддоменам по семантике dnsmasq.

Для этой области ответ `A` содержит sentinel; `AAAA`, `HTTPS` и `SVCB` не должны возвращать адреса или параметры альтернативного подключения. Адаптер проверяет фактические DNS-пакеты для этих четырёх типов. Одного наличия строк в конфигурации для успешного `status` недостаточно.

Глобальный `filter_aaaa` не включается. DNS и IPv6 других доменов сохраняют настройки владельца. Собственный DoH/DoT клиента и закешированные до изменения ответы могут обходить DNS роутера; проверка адаптера относится к указанному локальному резолверу.

### Runtime и сборка выпуска

Штатный запуск идёт через release manager: компонент `r2o-telegram` с аргументом `--rt-proxy`. В выпуске `r2o-telegram` является applet контроллера; диспетчер находится в [main.rs](../crates/r2o-controller/src/main.rs), список applet — в [controller-applets](../router/controller-applets).

При изменениях Rust-прокси необходимо пересобрать **контроллер для целевой архитектуры** и соответствующий applet выпуска. Обновления shell-скриптов или отдельной библиотеки недостаточно для замены уже упакованного runtime. В архив должны входить актуальные `S99r2o`, оба RT-адаптера и пересобранные бинарники; их состав задаёт [package-release.sh](../scripts/package-release.sh).

На Keenetic запуск команд с позиционными аргументами использует проверенную Entware shell. Штатный `/bin/sh` прошивки может быть NDM-обёрткой, теряющей аргументы после `-c`; совместимость этого пути проверяется отдельной регрессией.

## Готовность, восстановление и остановка

Порядок запуска: listener прокси → проверка готовности → firewall → DNS. Rust runtime публикует marker `R2ORT1 PID адрес:порт` после открытия listener. Служба сверяет живой процесс, его назначение, PID и порт из обычного health-файла; ссылка вместо health-файла не принимается. Для явно настроенного внешнего `R2O_RT_PROXY_BIN` проверяются исполняемый файл процесса и принадлежность слушающего сокета этому PID.

Готовность listener подтверждает возможность принимать соединения. Она сама по себе не доказывает доступность внешнего CONNECT-пула. Общая RT health-проверка дополнительно требует действующих правил firewall и правильных DNS-ответов. После перезагрузки firewall служба проверяет и восстанавливает свои правила; повторный успешный запуск не создаёт второй прокси.

При остановке сначала снимаются собственные DNS-настройки, затем завершается прокси и удаляется его NAT. Если DNS очистить не удалось, процесс, PID, health и журнал владения сохраняются для повторной попытки. Ошибка DNS или firewall при старте возвращает ошибку и вызывает очистку; если откат DNS тоже неуспешен, обслуживающий sentinel listener сохраняется. Uninstall также прекращает удаление файлов при ошибке очистки DNS или RT firewall.

### Владение и legacy

DNS записывает изменения в журнал `$STATE_DIR/rt-dns/owned.tsv`; по умолчанию это `/opt/r2o/state/rt-dns/owned.tsv`. Совпадающие настройки, существовавшие до R2O, не присваиваются автоматически. Очистка удаляет собственные значения и сохраняет изменённые владельцем записи. Чужие несохранённые изменения UCI `dhcp` не коммитятся адаптером.

iptables меняет собственные цепи и помеченные hooks через `iptables-restore --noflush`. nftables применяет собственную таблицу одним batch. `status` проверяет реальные правила и hooks. Чужая одноимённая структура приводит к отказу, а не к её удалению.

Старая `inet r2o_rt` мигрирует только после распознавания точной прежней структуры: две NAT-цепи и два REDIRECT для ожидаемых sentinel и порта. Удаление старой и установка новой таблицы выполняются в одной nft-транзакции. Legacy DNS очищается по сохранённому состоянию: распознаются прежние RT hostrecord/server и сохранённое значение `filter_aaaa`; изменённые владельцем секции сохраняются. Удалять журнал вручную до успешного `clear` нельзя: он нужен для восстановления после прерванной операции.

## Зависимости bootstrap

При включённом RT bootstrap проверяет dnsmasq и `nc`, используемый для запроса фактических DNS-ответов. Для iptables нужны `iptables-restore` и работоспособная таблица `nat`; для nft — штатные nftables и необходимые возможности ядра. На OpenWrt DNS-адаптер использует штатные `uci` и `/etc/init.d/dnsmasq`.

Если на Keenetic dnsmasq отсутствует или не запускается, устанавливается Entware `dnsmasq-full`. Пакет предоставляет общий `/opt/etc/init.d/S56dnsmasq`, но R2O использует частный listener на `127.0.0.1:5354`:

- При установке пакета передаётся **`IPKG_NO_SCRIPT=1`**, чтобы postinst не запускал общий DNS-сервис.
- Новый S56 получает `ENABLED=no`, в том числе после частичной установки с ошибкой.
- Существующий обычный S56 копируется до opkg и восстанавливается вместе с правами. Он не является conffile пакета и может быть заменён при reinstall.
- Резервная копия считается пригодной только после успешного копирования; при неудаче восстановления она сохраняется для восстановления владельцем.

## Диагностика установленного выпуска

Команды ниже предназначены для root на роутере. Они определяют активный слот из `release-slots`, поэтому не требуют угадывать имя выпуска:

```sh
r2o_root=${R2O_DIR:-/opt/r2o}
r2o_release=$(sed -n '2p' "$r2o_root/release-slots")
r2o_router="$r2o_root/releases/$r2o_release/router"

R2O_DIR="$r2o_root" "$r2o_router/S99r2o" status
R2O_DIR="$r2o_root" "$r2o_router/S99r2o" update-health
printf 'update-health rc=%s\n' "$?"

R2O_DIR="$r2o_root" "$r2o_router/r2o-rt-dns.sh" status
printf 'RT DNS rc=%s\n' "$?"

tail -n 100 "$r2o_root/log/rt-proxy.log"
```

У firewall-адаптера явно укажите используемый backend. Для Keenetic и fw3:

```sh
R2O_DIR="$r2o_root" R2O_FW=iptables \
    "$r2o_router/r2o-rt-firewall.sh" status
printf 'RT firewall rc=%s\n' "$?"
iptables -t nat -S R2O_RT_PRE
iptables -t nat -S R2O_RT_OUT
```

Для fw4:

```sh
R2O_DIR="$r2o_root" R2O_FW=nft \
    "$r2o_router/r2o-rt-firewall.sh" status
printf 'RT firewall rc=%s\n' "$?"
nft list table ip r2o_rt
```

При явном `FW_BACKEND` в конфигурации используйте соответствующий backend. Для нестандартных `R2O_CONFIG`, `STATE_DIR` и runtime-путей учитывайте настройки установленной службы. Лог частного dnsmasq Keenetic по умолчанию находится в `/opt/r2o/state/rt-dns/dnsmasq.log`. Код `0` у RT-адаптера означает успешную текущую проверку; ненулевой код требует изучения сообщения и состояния. Для общей проверки службы используйте `update-health`, поскольку `status` прежде всего выводит диагностический текст.

### Явное решение владельца отключить RT

`R2O_RT_PROXY=0` — поддерживаемая ручная настройка владельца в конфигурации R2O. После её изменения применяется штатный restart службы; RT DNS и NAT снимаются обычным порядком. Это сознательное отключение функции, **не исправление ошибки установки или работы RuTracker**. Автоматически заменять неисправный включённый RT этой настройкой нельзя. При ошибке DNS clear сохраняется возможность безопасно повторить остановку.

## Регрессионные проверки

Из корня репозитория:

```sh
sh scripts/test-router-keenetic-shell-argv.sh
sh scripts/test-router-install-bootstrap.sh
sh scripts/test-router-rt-firewall.sh
sh scripts/test-router-rt-lifecycle.sh
sh scripts/test-router-uninstall-fallback.sh
cargo test -p r2o-telegram --lib rt_proxy::tests
```

Firewall-регрессия моделирует состояния CLI и ошибки применения; lifecycle использует настоящий launcher, ELF-процесс и TCP listener с fixtures DNS/firewall. Эти проверки дополняют испытания настоящих сетевых компонентов.

Для live DNS нужны **реальные** `dnsmasq`, `uci`, `nc` и Python 3; допустим запуск подходящих бинарников через подготовленную QEMU-обёртку. Укажите действительные пути:

```sh
R2O_TEST_DNSMASQ_BIN=/путь/к/dnsmasq \
R2O_TEST_UCI_BIN=/путь/к/uci \
R2O_TEST_NC_BIN=/путь/к/nc \
    sh scripts/test-rt-dns-live.sh
```

Тест отправляет настоящие DNS-пакеты в изолированное тестовое окружение. Его сервисная обёртка переводит реальные UCI-значения в параметры реального dnsmasq; она не является испытанием всего OpenWrt procd/ubus. Keenetic NDM в этом тесте проверяется как CLI-контракт с отдельным fixture, а не как работающий закрытый демон прошивки.

Для самостоятельной проверки runtime предусмотрен [test-rt-proxy-live.py](../scripts/test-rt-proxy-live.py) с обязательными `--binary` и `--output`. Он использует локальные TLS/CONNECT endpoints; бинарник должен соответствовать проверяемой архитектуре и поддерживать RT applet. Проверка через этот driver не заменяет проверку DNS и firewall на роутере.

## Границы доказательств

Подтверждены компонентные проверки с настоящими Entware MIPSEL/iptables 1.4.21 и OpenWrt fw4/nftables в QEMU: установка и состояние правил, повторное применение, восстановление после удаления hook/таблицы, реальный TLS через OUTPUT REDIRECT, сохранение чужих правил и очистка. Отдельно проверены настоящий opkg с оригинальным `dnsmasq-full`, отключение нового S56 и восстановление существующего после реального reinstall.

Vendor kernel для MIPSEL адаптирован под плату QEMU Malta. Это не эмуляция всего аппаратного обеспечения KN-1910/KN-1913 и не подтверждение работы на физических роутерах. Проверки DNS с настоящими UCI/dnsmasq и NDM-контракт проверяют разные уровни; успешный NDM fixture не доказывает поведение закрытого NDM на каждой прошивке.

Компонентный OUTPUT-тест не подтверждает автоматически путь клиента через LAN PREROUTING, внешнюю доступность RuTracker, работу всех провайдеров или полный установочный сценарий OpenWrt. Для таких утверждений нужны отдельные сохранённые журналы соответствующего интеграционного прогона. Настоящий документ не заявляет аппаратный PASS или 100% совместимость со всеми платформами.
