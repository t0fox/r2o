# R2O Universal Update Engine

База исходников — выпуск `r2o-20261122-1125-6b5c711-45017277844-1` и коммит `6b5c711c`. Публичная история формата 2 начинается с подписанного выпуска [`r2o-20261122-1406-a39e835-45031058272`](https://github.com/t0fox/r2o/releases/tag/r2o-20261122-1406-a39e835-45031058272). Для прежних пакетов предусмотрена чистая установка.

## Причины отказов

- Долгая команда установки занимала общий флаг управления панели. Состояние команды жило в памяти процесса, который сам перезапускался при установке.
- Манифест и подпись скачивались через два независимых запроса к изменяемому адресу `latest`. Публикация между запросами могла дать несовпавшую пару. Архив загружался только с GitHub, а обрыв приводил к удалению частичного файла.
- Менеджер копировал архив в рабочий каталог, а после распаковки снова копировал дерево релиза при активации. Расход места зависел от фазы, а точный размер распаковки заранее отсутствовал.
- Переключение слотов и запись результата проверки разделялись. Сбой после переключения мог оставить активный выпуск до проверки служб. Адаптер после первой успешной пробы ждал фиксированные 60 секунд.

## Архитектура

Панель принимает команды того же источника и запускает Rust-процесс `r2o-manager`. Панель читает локальный статус по `GET /api/update` и список проверенных версий по `GET /api/update/catalog`. Проверка обновлений и установка используют отдельный флаг панели. Блокировка менеджера действует между процессами, в том числе после перезапуска панели. До опасной фазы можно запросить отмену.

1. **CHECK.** GitHub Releases определяет опубликованный стабильный тег. При отказе API менеджер берёт его из HTTPS-перенаправления `latest/download/catalog.json` на каталог того же репозитория. Менеджер проверяет Ed25519 каталога, привязку к тегу и возрастающий порядковый номер. Выбранный манифест скачивается по закреплённому тегу и сверяется с каталогом.
2. **DOWNLOAD.** Менеджер резервирует место по подписанным размерам. Rust HTTPS измеряет скорость пробных диапазонов и пробует источники по порядку. Частичный архив хранится под именем подписанного SHA-256. Ответ `206` должен содержать точные значения `Content-Range` и длины. Ответ `200` начинает загрузку файла заново. После возобновления проверяется хеш всего архива.
3. **VERIFY и STAGE.** Менеджер проверяет хеш, правила распаковки, лимиты, архитектуру ELF и ожидаемый загрузчик. Проверенное дерево синхронизируется с диском до остановки служб.
4. **MIGRATE.** Менеджер сверяет контракт форматов и проверяет схему обученного каталога. Выпуски формата пакета 2 разделяют форматы конфигурации и состояния версии 1. Миграция телеметрии обновлятора выполняется атомарной записью. Переход на будущие форматы пользовательских данных потребует реализованной прямой и обратной миграции.
5. **ACTIVATE.** Менеджер синхронизирует журнал на диске, останавливает службы через адаптер, переносит готовое дерево и атомарно записывает слоты. Рабочий предшественник сохраняется. Конфигурация и каталог остаются в общих путях вне слотов.
6. **HEALTH CHECK и COMMIT.** Проверяется активный слот и несколько последовательных проб служб. Адаптер проверяет NFQUEUE для включённых семейств, сокеты и публикацию статуса контроллера, правила firewall, DNS recovery, HTTP API панели и готовность включённого Telegram. После успеха Rust отмечает фиксацию в журнале и обновляет историю. При отказе восстанавливает прежний слот. Временный процесс восстановления остаётся доступным после остановки панели и при аварийном завершении основного процесса. При старте OpenWrt или Keenetic журнал обрабатывается до обычного запуска служб.

## Матрица совместимости

| Установленный выпуск | Целевой выпуск | Поведение |
|---|---|---|
| Установка отсутствует | Первый выпуск формата 2 | Чистая подписанная установка. |
| Пакет прежнего формата | Любой выпуск формата 2 | Менеджер отклоняет сетевое обновление имеющейся установки. |
| Формат пакета 2, конфигурация 1, состояние 1 | Более новый выпуск той же схемы и ABI | Обновление с теми же пользовательскими данными. |
| Формат пакета 2, конфигурация 1, состояние 1 | Более старый опубликованный выпуск той же схемы и ABI | Явный downgrade через каталог. Предыдущий локальный слот доступен без сети. |
| Любой поддерживаемый выпуск | Неизвестная схема или другой ABI | Отказ до остановки служб и переключения слотов. |

## Публикация зеркала

Матрица CI собирает 12 ABI и хранит артефакты семь дней. Ручной Release выбирает успешный CI для точного SHA `main`, сверяет успешную попытку сборки каждого ABI, скачивает 12 артефактов по ID и проверяет SHA-256 бинарников и ELF перед упаковкой. Частичный перезапуск CI использует артефакты успешных заданий предыдущих попыток того же прогона. Тег и заголовок определяются датой коммита, его SHA и ID прогона CI. Если артефакты истекли, запусти CI снова для нужного SHA. Режим `validate_only` проверяет этот путь до упаковки без доступа к окружению подписи.

Workflow проверяет подпись и архивы в черновике GitHub Releases. Если настроено R2, он копирует оригинальные файлы и сравнивает скачанные байты. Указатель зеркала меняется после проверки обязательных файлов и публикации тега в GitHub. Для R2 нужны переменные `R2O_R2_PUBLIC_URL`, `R2O_R2_ENDPOINT`, `R2O_R2_BUCKET` и секреты `R2O_R2_ACCESS_KEY_ID`, `R2O_R2_SECRET_ACCESS_KEY` в окружении подписи. Публичные прокси получают только ссылки на публичные активы.

## Проверка

Команды локального прогона

```sh
cargo fmt --all --check
cargo check --locked --workspace --all-targets
cargo test --locked -p r2o-manager -p r2o-panel --all-targets
sh scripts/test-package-release.sh
sh scripts/test-router-install-bootstrap.sh
sh scripts/test-router-update-lifecycle.sh
R2O_PANEL_BIN=target/debug/r2o-panel node crates/r2o-panel/tests/browser.cjs
```

Сценарий аварийного отключения в полном OpenWrt QEMU принимает исходное ядро, сжатый ext4-образ, ARM64-менеджер и каталог логов. QEMU выключается принудительно и загружается снова с тем же диском. По умолчанию момент отключения задаёт тестовый адаптер при остановке служб, запуске после переключения слотов и проверке готовности. С `--strace-packages` можно также остановить менеджер после подготовки отката или записи флага коммита в журнал. Опция принимает каталог с APK `strace` и подписанным `packages.adb` от соответствующей сборки OpenWrt. Гость проверяет подпись индекса при установке пакета.

```sh
python3 scripts/test-router-update-powercut-qemu.py KERNEL ROOTFS_GZIP ARM64_MANAGER LOGS
```

Параметр `--public-update ARCHIVE MANIFEST` вместе с `--strace-packages` добавляет ранние фазы с публичным ARM64-архивом. Гость подключается к GitHub через сеть QEMU. После каждой аварии проверяются активный и предыдущий слоты, состояние журнала, отсутствие осиротевших каталогов распаковки и сохранность файлов пользователя. Параметр `--phase` позволяет повторить выбранные случаи.

Отдельной проверки требуют трафик через NFQUEUE на физическом устройстве, внешний DNS и Telegram, сбой питания физического накопителя, скорость WAN и доступность зеркал у операторов. Базовый пакет доступен в GitHub Releases без настройки Cloudflare R2.

### Выполненные проверки

- В изолированном Linux на E: прошли 38 тестов библиотеки менеджера, 19 CLI-тестов и 32 теста панели. Успешно завершился `cargo check --locked --workspace --all-targets`. Отдельно прошли три теста сборщика каталога.
- CLI проверил отказ неизвестной схемы каталога, сохранение ошибки для панели, возврат рабочего выпуска при ошибках запуска и остановки кандидата, запрет параллельной установки и поздней отмены, восстановление после SIGKILL и повторную установку. Тест с тремя слотами подтвердил сохранение предыдущего рабочего выпуска при отказе нового.
- С публичным архивом на Linux проверены отмена и SIGKILL на стадии `download`. В обоих сценариях исходный слот остался активным, вызовов тестового адаптера служб не было. Повторная попытка докачала пакет и завершила транзакцию.
- Упаковка и чистая подписанная установка прошли локально. Для всех 12 ABI собран и запущен менеджер. На каждом он проверил Ed25519, SHA-256, ELF и установил подписанную файловую фикстуру. Проверено в QEMU user mode, для x86_64/musl на Linux. Фикстура использует ELF менеджера для всех компонентов. Она проверяет упаковку и работу установщика на ABI.
- Браузерный тест Chrome прошёл за 58,29 с. Он проверил обновление интерфейса после получения каталога, выбор downgrade и зеркала, сохранённую причину отказа и потерю связи во время перезапуска.
- OpenWrt ARM64 QEMU проверил слоты, конфигурацию и каталог после пяти отключений на пути локального отката. До записи журнала удаляется незавершённая подготовка. При сбое после переключения менеджер возвращает рабочий слот и записывает отказ кандидата. После записи флага коммита подтверждённый слот сохраняется, повторное восстановление не дублирует историю. Пять отключений и пять повторных загрузок заняли 55,62 с.
- Дополнительные отключения с публичным подписанным ARM64-пакетом прошли в `check`, `download`, `verify`, `stage` и `migrate` до активации. После каждой повторной загрузки исходный слот оставался активным, файлы пользователя сохранялись, незавершённые каталоги подготовки удалялись. После отключения в `migrate` в том же госте проверена повторная установка: публичный пакет занял активный слот, исходный выпуск доступен для отката.
- Отдельный прогон в OpenWrt 25.12.6 ARM64 QEMU прошёл со штатным адаптером, рабочими ELF-компонентами и модулями ядра OpenWrt. При локальном downgrade сохранился каталог, обе очереди NFQUEUE имели обработчик, HTTP API панели ответил, а менеджер записал успешную проверку готовности. Весь прогон занял 109,13 с, интервал от подготовки слота до записи результата составил 37 с. Для гостя использовались только loopback и конфигурация с выключенными Telegram, Meta DNS и RuTracker.

### Замеры доступности

Из Windows для одного запроса `Range: bytes=0-16383` к архиву текущего публичного релиза все четыре пути вернули HTTP 206 и 16 384 байта.

| Источник | Время ответа |
|---|---:|
| GitHub | 1,79 с |
| gh-proxy.com | 2,86 с |
| ghfast.top | 2,90 с |
| ghproxy.net | 11,92 с |

Этот замер фиксирует доступность диапазона с данного хоста. В отдельном тесте на x86_64/musl менеджер докачал 4 899 427 байт публичного архива через GitHub за 15,02 с полного цикла. Затем каждый из четырёх источников по очереди блокировали в пространстве имён стенда. Во всех случаях менеджер докачал архив через другой источник, сохранил конфигурацию и оставил прежний слот доступным. Полный цикл занял 16,10–30,87 с. При отдельной блокировке `api.github.com` новая сборка x86_64/musl определила тег через `github.com` и проверила подписанный каталог за 2,46 с с пиковым RSS 2 372 КиБ. Время WAN-загрузки всего архива на физическом роутере требует отдельного прогона.

Изолированный x86_64/musl стенд. Архивы по 10,67 МиБ содержали 22,26 МиБ файлов. Локально подписанные пакеты содержали реальные ELF-компоненты. Службы при переключении слотов имитировал адаптер теста.
