## Packet path and state

D2O datapath/d2kd.c main opens/configures raw-send and NFQUEUE resources, optionally opens the control socket, polls queue/control descriptors, parses each netlink packet, selects the normal or controller-probe session entrypoint, applies an MTU-derived TCP segment cap when required, and issues accept/drop/replacement verdicts. The loop also flushes held TCP/UDP packets, emits due raw work, advances UDP receive sequencing, pumps control events, and periodically sweeps and expires session state.

R2O crates/r2o-datapath/src/main.rs run owns the equivalent daemon loop. It combines QueueSocket receive deadlines with scheduler, hold, UDP-deferred-verdict, route-refresh, and stats deadlines; route notifications trigger netlink refresh; control commands produce ACKs and update name plans. ReceiveError::Wait represents poll failures and retries without flushing; Interrupted and WouldBlock are no-read results; LostPackets and other recv I/O errors flush held/deferred packets, report the error, and continue the loop. Packet decisions are delegated to engine.rs and the session/packet helpers below.

The observable packet branches include: missing or truncated queue payload; controller-probe mark versus ordinary traffic; standard versus MTU-capped TCP execution; accept/drop/replacement; queue receive loss/interruption/fatal error; raw-send failure; and delayed verdict release. Timer-driven transitions include one-second session sweeps, session expiry, UDP receive-window expiry, held-packet deadlines, scheduled raw sends, and route refresh. Side effects include NFQUEUE verdicts, raw packet sends, control ACK/events, journal updates, route/conntrack queries, and diagnostics.

### HTTP response-reader branch audit (2026-11-01)

D2O `verify.c:read_status_rd` calls `read_status_buf` and `read_http_body`; `request_page_budget` is the production GET caller and consumes interim responses, redirects, framing metadata, and the final outcome. R2O `fetch.rs` owns socket reads, deadlines, and metadata/classification around `HttpResponseParser`; `r2k-core/src/http_response.rs` implements incremental framing used by normal fetches and the HEAD drain path.

The parsers agree on HTTP/1.0-1.1 status bounds, fragmented headers/bodies, skipping 1xx except 101, duplicate numerically equal Content-Length, one `chunked` transfer encoding, CL+TE rejection, fixed/chunked/close-delimited completion, and a 65,536-byte header limit. The clean D2O `test_verify_http` passed in the recorded core run; the focused Rust `http_response` target now passes 10/10.

The C fixture in `core/test_verify_http.c` expects a 160-byte chunk-size line to stop at its `char line[128]` local limit. Rust previously accepted it with `LINE_CAPACITY=512`; the `rejects_chunk_size_line_beyond_d2o_buffer_limit` regression fixed the broad overflow. A production C/Rust boundary differential now confirms 127 content bytes are accepted and 128 rejected, matching the C buffer, and the focused Rust target passes 10/10.

The slice remains partial. D2O treats chunk extensions and trailers as opaque and skips colonless header lines; Rust matches malformed extension syntax and colonless header behavior, and tolerates control bytes only after the chunk-extension `;`. D2O also leaves non-NUL control bytes in header fields opaque while rejecting control bytes in the status line. Rust tracks that status-line boundary without relaxing header NUL validation. In fields, D2O `find_eol` recognizes only CRLF; Rust now preserves lone CR/LF as field bytes too, so an apparent next header after a bare LF can remain part of an ignored field value. Trailer lines match D2O for opaque controls and its C-string rule: a leading NUL ends the trailer list. `test-http-chunk-framing-differential.sh` pins D2O main `a63d9641f4e00aa35fa1e5ccbda47bb5f310c0fe` and compares sixteen vectors against the production C reader and Rust parser, including extension/header/trailer controls, lone field CR/LF, the leading-NUL trailer case, and 204/304 responses whose buffered bytes are ignored at the header boundary. Status, completion, and body-byte results match. Other framing branches and the full reader call path remain open.

### Панель, router, Telegram и VPS

- Панель: 68 production-функций C (`panel/main.c`, `panel/server.c`). Rust `r2o-panel` покрывает endpoints, config parser, лимиты, таймауты, assets и browser-flow; 22 differential-сценария закреплены на `304ba893` и требуют перепина/повторного прогона на текущей ревизии. Детали — `docs/audit/panel-router-vps-telegram-audit.md`.
- Router/service/firewall/release: shell-функции D2O (`S99d2k`, `d2k-openwrt-init`, `d2k-fw-heal.sh`, `d2k-ppe-deoffload.sh`, `d2k-tg-firewall.sh`, `d2k-tg-watchdog.sh`, `d2k-update.sh`, `d2k-instagram-dns.sh`, `install.sh`) сопоставлены с `router/*` и `r2o-manager`; большинство контрактов — service/helper fixtures, не live kernel/OpenWrt. Установка/rollback/подпись проверены на static-musl, физический роутер и полный procd/reboot — нет.
- Telegram: R2O `r2o-telegram` — перенос из Rust-донора z2kOW `tg-proxy`, а C11 D2O не является источником. Сравнение 38 файлов донора — source audit, не поведенческий differential. C-only функции D2O Telegram (например, `mtproto_auth.c`, `mtproto_probe.c`, `epoll_proxy.c`) не являются обязательными к переносу; для них статус `not-applicable`, а не «недоперенесено». Два исторических differential (route/DNS и response observer) закреплены на `304ba893` и в этом окружении не перезапускались.
- VPS `relay-enroll` (45 production-функций) и `relay-gate` (18) — отдельные сервисы с systemd units. R2O README явно исключает обязательный VPS/relay/WARP; их серверные реализации не переносятся и не входят в router-runtime матрицу. Router-side Meta DNS (`/resolve`) и install fallback (`D2K_GATE`) остаются в соответствующих строках.

### Совместимость control/plan

Аудит выявил не только пробелы тестов, но и фактические несовместимости:

- C `plan_parse.c` требует `D2KP`, R2O `r2k-core/src/plan.rs` требует `R2OP`; D2O-план отвергается R2O.
- C `plantlv.c` принимает текст `d2k-plan`, R2O `plan_text.rs` — `r2o-plan`.
- C control protocol version 22, R2O — 48; событие `0x000D` в C — `D2K_EV_CLIENT_TCP`, в R2O — `EVENT_R2O_VOICE_SUSPECT`.
- C control out ring 64 КиБ, R2O 128 КиБ.
- C plan tables ёмкостью `--flows` (2048), R2O — 128/128/64 и др.
- C `D2K_POISON_TS_UP` (`tcp_ts_up`) не реализован в R2O.
- C datapath принимает `--flows`, `--sched-slots`, `--duration`, `--log`, `--health-file`, `--udp-reverse-hook`; R2O переименовал часть и не принимает остальные.
- C `d2kc` принимает `--measure-mark`, `--health-file`, `--log`, `--https-cache`, `--self-check`, `--release-id`; R2O `--serve` их не знает.
- D2O пишет heartbeat `D2KH1 ...`; R2O panel пишет `R2OH1 ...`, datapath/controller heartbeat отсутствует.

Эти пункты добавлены в уточнённую матрицу как отдельные контракты с 0 баллов до появления paired differential на принятой ревизии.

### Итог

Инвентарь больше не ограничивается примечанием «остальные модули не покрыты»: для каждого production-файла определён Rust-владелец, а для неполных модулей перечислены конкретные непокрытые ветви. При этом ни один из перечисленных модулей не объявляется полностью перенесённым. Текущая строгая оценка после нормализации 2026-11-08 — **84/261 = 32,18 %** (только доказательства на `a63d964`/`a378e23`/`8e2c981`, 173 контракта); carry с явно помеченными `304` — **147/261 = 56,32 %**; legacy-агрегат — 80/89 = 89,89 %, но он не является оценкой текущей ревизии.
