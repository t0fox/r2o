# Горячий путь Rust относительно `8817879`

`stable-baseline-8817879` указывает на утверждённый `88178796374d83aa90267f0a4f103431112e1d23`. Измерения выполнены локально на образах из [QEMU-стенда](../../scripts/qemu-platform/README.md). Изменение движка ограничено `HoldTable` в datapath. Контроллер, платформенные адаптеры, правила очередей и период записи каталога использованы из baseline.

## Обход таблиц и буферы

Итерация `Vec` ограничена числом занятых элементов, пустые пачки не выделяют
память, а NFQUEUE отдаёт полезную нагрузку как `&[u8]` из переиспользуемого
буфера. При удержании пакет копируется, чтобы пережить повторное использование
буфера. Измерения ниже проверяют повторные обходы `HoldTable`.

В `HoldTable::feed_observing_mode` переиспользуется результат поиска SYN-якоря. Очистка `syns` начинается, когда наступил ближайший возможный срок истечения. При обновлении записи прежний срок служит нижней границей, а очистка проверяет срок каждого якоря по его актуальному `seen`. Регрессионный тест проверяет границу TTL, обновление `seen` и вход с более ранним временем.

## Микропрофиль

`scripts/qemu-platform/hold-hot.rs` вызывает `HoldTable::feed_observing` на неизменном пакете ACK с TCP-данными. В каждой серии 250 000 пакетов. Варианты чередовались в шести парах. При непустой таблице пакет соответствует последнему якорю. Микротест измеряет время обработки этой ветки, число вызовов аллокатора и объём выделенной памяти. Обе версии выполнили её с нулём аллокаций.

Для повторения соберите `r2o-datapath` с `--lib --release`. Свяжите `hold-hot.rs` через `rustc` той же версии и цели с точным `.rlib` из вывода Cargo. Для текущего release-профиля нужны `-C opt-level=3 -C panic=abort -C lto=fat` и `-L dependency=<target>/<архитектура>/release/deps`. Для сравнения используйте одно число пакетов, одинаковое заполнение и чередующийся порядок запусков.

| SYN-якоря | Медиана, мс за 250 000 пакетов, baseline → кандидат | Медиана парной разницы |
| ---: | ---: | ---: |
| 0 | 15,62 → 15,33 | −1,2% |
| 64 | 89,34 → 32,46 | −63,3% |
| 512 | 665,48 → 126,87 | −81,3% |
| 1024 | 1 329,02 → 200,42 | −84,7% |

## OpenWrt с реальной NFQUEUE

Шесть чередующихся пар на Linux 6.12.94, по 1 500 TCP-соединений с полезной нагрузкой 16 КиБ каждое. Использованы `PORTS=443`, окно `CONNBYTES=0:8` и одинаковые правила firewall. Контрольный порт 445 проходит вне очереди. Предел conntrack поднят с 14 848 до 65 536 только в изолированном бенчмарке. Ранние серии содержали паузу около 75 с после заполнения исходной таблицы. Итоговая серия завершилась при 20 037 записях и без этой паузы.

| Тракт | Мбит/с, baseline → кандидат | CPU datapath, с | Пакеты NFQUEUE | Потери NFQUEUE | RSS datapath, КиБ |
| --- | ---: | ---: | ---: | ---: | ---: |
| TCP/443 с NFQUEUE | 23,82 → 28,22 | 7,84 → 6,58 | 37 317 → 37 072 | 0 → 0 | 4 538 → 4 528 |
| TCP/445 вне NFQUEUE | 142,14 → 143,74 | 0,00 → 0,00 | 0 → 0 | 0 → 0 | 4 538 → 4 528 |

Парная медиана TCP/443 составляет +16,2% по пропускной способности, −15,0% по CPU и −14,5% по CPU на пакет из очереди. Диапазоны пар составили −13,3…+32,0% по скорости и −26,6…+12,0% по CPU. Число пакетов в очереди менялось по парам в пределах −1,25…+0,22%. Для TCP/445 парная медиана −4,1%, диапазон −23,0…+18,7%. Устойчивый сдвиг скорости вне NFQUEUE не подтверждён. Версия только с переиспользованием поиска в первой серии повысила парную медиану CPU на 8,1%, поэтому в кандидат вошёл вариант с очисткой по сроку.

Размер x86-64 musl `r2o-datapath` изменился с 1 726 368 до 1 726 720 байт (+352). MIPS32r2 little-endian soft-float изменился с 2 050 920 до 2 051 816 байт (+896).

## Подбор и полноценный ответ LAN

В каждой ячейке указаны секунды от первого запроса к цели до подтверждения плана, полного LAN-ответа и видимости привязки в файле каталога соответственно. Прикладная проверка требует проверенный сертификат, HTTP 200 и ожидаемое тело. Второй сценарий направлен на `b.example.net` и `198.51.100.6` при уже сохранённом результате для `a.example.com` и `198.51.100.2`. Первый запрос ко второй цели тоже должен не получить полный ответ. Поиск проверяется по новой привязке и отдельной записи о подтверждении в контроллере.

| Гость | Сценарий | Baseline, с | Кандидат, с |
| --- | --- | --- | --- |
| Viva KN‑1910 | Первый | 7,75 / 8,48 / 59,57 | 7,79 / 8,42 / 59,63 |
| Viva KN‑1910 | Новый аналогичный | 7,71 / 8,27 / 60,10 | 7,67 / 8,19 / 60,24 |

Точки наблюдаются с шагом до секунды. Оба сценария доступны примерно через 8 с. Сохранение происходит около очередного 60-секундного цикла каталога. Измерения не подтверждают изменения скорости алгоритма подбора. На OpenWrt также пройдены LAN HTTP/3, включая контрольный HTTP 503, и DNS UID reconciliation. В госте прошли 472 теста библиотеки datapath и 93 теста его бинарника. Ещё 23 теста библиотеки помечены `ignored` в исходниках.

## RSS после прогрева

Суммарный RSS datapath и controller на OpenWrt с baseline составил 9 492 КиБ в первом замере, 10 448 КиБ на 603-й секунде и 11 264 КиБ на 1 206-й. Из 816 КиБ роста во второй половине 580 КиБ пришлось на controller и 236 КиБ на datapath. Последние два замера совпали, а предшествующие продолжали расти. Стабилизация на длительном интервале не подтверждена.

В отдельном запуске того же baseline после прогрева без дальнейших запросов RSS вырос с 9 484 до 9 700 КиБ за 301 с. Всё изменение попало в `RssAnon`. `RssFile` обоих процессов не изменился. Наблюдения показывают рост резидентной анонимной памяти даже без клиентской нагрузки. Эти измерения не определяют причину роста и не подтверждают утечку.

В сопоставимом 603-секундном прогоне итоговый кандидат вырос с 9 492 до 10 108 КиБ против 10 448 КиБ у baseline на той же отметке. На последнем 30-секундном интервале кандидат добавил 20 КиБ. Все 126 ответов дошли до LAN-клиента без потерь NFQUEUE. PID не менялись и дескрипторы не накапливались. Удаление восстановило исходные настройки гостя.

## Очередь HTTP и источники DNS

В `0d883b7` срок хранения HTTP-потока проверяется по ближайшему дедлайну,
а TCP/443 не просматривает HTTP-таблицу. Ожидание обрыва незавершённого ответа
тоже имеет ближайший дедлайн. Буфер событий создаётся при первом реальном
обрыве. Дедлайны сохраняют исходную строгую границу TTL. Таймер сессий
освобождает просроченные HTTP-записи и при длительном отсутствии HTTP-трафика.

Медианы шести пар по 300 000 пакетов TCP/443 при 129 одинаковых SYN-якорях.
Сравнивались `09b3f8d` и `0d883b7`. Счётчик аллокаций внутри цикла
показал ноль в обеих сборках.

| HTTP-записи | Было, мс | Стало, мс |
| ---: | ---: | ---: |
| 0 | 45,16 | 37,26 |
| 64 | 128,92 | 37,12 |
| 128 | 207,19 | 34,64 |

OpenWrt 6.12, шесть чередующихся пар, по 24 576 000 байт в каждом прогоне.
Обе сборки использовали статический musl и одинаковый firewall.
Медиана покрытия TCP/443 составила 37 060 и 37 094 пакетов NFQUEUE.
На TCP/445 очередь не получала пакетов.

| Метрика OpenWrt | Было | Стало |
| --- | ---: | ---: |
| TCP/443 через NFQUEUE, Мбит/с | 26,99 | 28,39 |
| CPU datapath на TCP/443, тики | 674 | 650,5 |
| RSS datapath, КиБ | 4544 | 4540 |
| TCP/445 вне NFQUEUE, Мбит/с | 152,98 | 145,91 |
| Потери NFQUEUE во всех прогонах | 0 | 0 |
| Бинарник datapath, байт | 1 726 720 | 1 727 184 |

Разница на TCP/445 зафиксирована в виртуальном стенде. Проход трафика
за пределами очереди подтверждён счётчиками. Профиль `strace` прежней серии
показал приблизительно по одному `poll`, `recvfrom` и `sendto` на пакет.
Обычный вердикт уже строится в стеке, пакет заимствуется из буфера.
`recvmmsg` может дать выигрыш при наличии нескольких готовых дейтаграмм.
Изменение схемы чтения потребовало бы замеров задержки control-сокета и
подтверждения той же обработки переполнения на старых ядрах.
Все эти вызовы остались на штатном пути.

DNS-контроллер использует текущую конфигурацию, запущенный экземпляр
OpenWrt procd и свежую запись о DNS-запросе. Для RCI, ndmc и logread
контроллер запоминает позицию в журнале. Старые записи, совпавший SNI и обычный APPLIED перестали
подтверждать использование DNS. Адресный Recovery начинает работу после
свежего события DNS-службы и двух сетевых ошибок своего измерения.
В панели состояния разделены на конфигурацию, работающий upstream,
наблюдавшееся обращение, результат проверки и недоступный источник.
Пассивный HTTPS от LAN-клиента не добавляет системный DNS роутера.
В штатном OpenWrt procd проверились обычный системный DNS, конфигурация
остановленной службы со старой записью журнала, смена и отключение
upstream. Отдельные loopback-тесты прошли DoH, DoT, DoQ и DoH3.

На Hopper команда `--platform down` вернула `EAGAIN` при удержании flock
рабочим потоком во время чтения DNS через ndmc. После переноса чтения
за пределы транзакции команда завершилась кодом 0, пока ndmc ещё выполнялся.
Поздний результат не восстановил выключенные правила. Повторный запуск
подтвердил bind NFQUEUE. Таймер каталога по-прежнему составляет 60 с.

### Анонимная память OpenWrt

Счётчик оборачивал системный Rust-аллокатор в двух отдельных диагностических
сборках datapath из `8817879` и `0d883b7`. Controller остался одинаковым.
За 153 и 151 с гостевого времени выполнено 5 и 6 циклов по шесть ответов
TCP, UDP и DNS на IPv4/IPv6. Из-за пропущенной точки базового замера число
циклов в конце различается. Для одинаковых пяти циклов RSS сравнивается
на 153-й и 121-й секундах соответственно.

| Показатель datapath | База | Кандидат |
| --- | ---: | ---: |
| Живой heap в начале, байт | 2 933 468 | 2 933 468 |
| Живой heap после прогрева, байт | 2 947 884 | 2 947 884 |
| RssAnon в начале, КиБ | 2196 | 2196 |
| RssAnon после пяти циклов, КиБ | 2456 | 2384 |
| RssAnon в последней точке, КиБ | 2456 | 2436 |
| RssFile, КиБ | 1760 | 1760 |

Живой heap прибавил 14 416 байт и четыре блока в диапазоне 257–65 536
байт. После этого фиксированные размеры и число живых блоков сохранялись,
а счётчик новых вызовов аллокатора продолжал расти. Анонимный RSS
продолжил расти после стабилизации живых аллокаций. Такой профиль
совместим с прогревом страниц и удержанием памяти аллокатором. Гостевое ядро OpenWrt
не предоставляет `smaps`, поэтому эксперимент не разделяет эти эффекты
по отображениям и не указывает отдельное место выделения. PSS на
Keenetic измерялся в предыдущей серии с предшествующим кандидатом.

### Viva KN-1913

Стенд использует оригинальный SquashFS именно KN-1913 из KeeneticOS 5.1.8.
В извлечённом `bin/ndmc` подтверждены MIPS32r2 little-endian и
`ld-musl-mipsel-sf.so.1`. Виртуальная память установлена в 256 МБ по
[справочнику KN-1913](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.0/ru/cli_manual_kn-1913_ru.pdf).
Гость использует адаптированное ядро производителя 4.9 для Malta и
существующий эмулятор событий NDM. Штатный ndmc не получил ответа на
свой IPC-запрос. Аппаратное ускорение платы этот стенд не выполняет.

| Сценарий KN-1913 | Подтверждение плана, с | Полный HTTPS-ответ LAN, с |
| --- | ---: | ---: |
| Холодный подбор | 7,71 | 8,26 |
| Подбор для нового имени и IP | 7,57 | 8,52 |

Обе привязки записались при SIGTERM. После запуска с выключенным
автопоиском их полные LAN-ответы пришли за 0,54 и 0,71 с соответственно.

В изолированном прогоне OpenWrt прошли LAN HTTP/3, маршруты DNS с UID
и оба сценария TLS в apply. Полный LAN-ответ пришёл за 8,37 с в холодном
сценарии и за 7,47 с для новой цели. Периодическая запись заняла
59,79 и 60,15 с.

На Hopper изолированный повтор подтвердил запись каталога через 59,27 с.
После SIGKILL контроллера и замены процессов полный ответ LAN пришёл
за 0,64 с при выключенном автопоиске.
