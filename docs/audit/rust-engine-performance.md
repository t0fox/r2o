# Горячий путь Rust относительно `8817879`

`stable-baseline-8817879` указывает на утверждённый `88178796374d83aa90267f0a4f103431112e1d23`. Измерения выполнены локально на образах из [QEMU-стенда](../../scripts/qemu-platform/README.md). Изменение движка ограничено `HoldTable` в datapath. Контроллер, платформенные адаптеры, правила очередей и период записи каталога использованы из baseline.

## Применимость D2K

Коммит `df66e2b` сократил обход фиксированных C-таблиц до фактически использованных слотов и убрал обнуление буферов всей пачки. В Rust `Vec` уже ограничивает итерацию длиной, пустые пачки не выделяют память, а NFQUEUE отдаёт полезную нагрузку как `&[u8]` из переиспользуемого буфера. Копирование оригинала при удержании остаётся необходимым, поскольку время жизни оригинала больше времени жизни этого буфера. Изменение D2K подсказало проверить количество повторных обходов `HoldTable`. C-код и новые зависимости не переносились. `7241cd2` расширяет проверки для сборок роутеров, `ac90901` меняет загрузку Zig. [Диапазон D2K](https://github.com/necronicle/d2k/compare/fbad20e...ac90901).

В `HoldTable::feed_observing_mode` переиспользуется результат поиска SYN-якоря. Очистка `syns` начинается, когда наступил ближайший возможный срок истечения. При обновлении записи прежний срок служит нижней границей, а очистка проверяет срок каждого якоря по его актуальному `seen`. Регрессионный тест проверяет границу TTL, обновление `seen` и вход с более ранним временем.

## Микропрофиль

`scripts/qemu-platform/hold-hot.rs` вызывает `HoldTable::feed_observing` на неизменном пакете ACK с TCP-данными. В каждой серии 250 000 пакетов. Варианты чередовались в шести парах. При непустой таблице пакет соответствует последнему якорю. Микротест измеряет время обработки этой ветки, число вызовов аллокатора и объём выделенной памяти. Обе версии выполнили её с нулём аллокаций.

Для повторения соберите `r2o-datapath` с `--lib --release`. Свяжите `hold-hot.rs` через `rustc` той же версии и цели с точным `.rlib` из вывода Cargo. Для текущего release-профиля нужны `-C opt-level=3 -C panic=abort -C lto=fat` и `-L dependency=<target>/<архитектура>/release/deps`. Для сравнения используйте одно число пакетов, одинаковое заполнение и чередующийся порядок запусков.

## OpenWrt с реальной NFQUEUE

Шесть чередующихся пар на Linux 6.12.94, по 1 500 TCP-соединений с полезной нагрузкой 16 КиБ каждое. Использованы `PORTS=443`, окно `CONNBYTES=0:8` и одинаковые правила firewall. Контрольный порт 445 проходит вне очереди. Предел conntrack поднят с 14 848 до 65 536 только в изолированном бенчмарке. Ранние серии содержали паузу около 75 с после заполнения исходной таблицы. Итоговая серия завершилась при 20 037 записях и без этой паузы.

| Тракт | Мбит/с, baseline → кандидат | CPU datapath, с | Пакеты NFQUEUE | Потери NFQUEUE | RSS datapath, КиБ |
| --- | ---: | ---: | ---: | ---: | ---: |
| TCP/443 с NFQUEUE | 23,82 → 28,22 | 7,84 → 6,58 | 37 317 → 37 072 | 0 → 0 | 4 538 → 4 528 |
| TCP/445 вне NFQUEUE | 142,14 → 143,74 | 0,00 → 0,00 | 0 → 0 | 0 → 0 | 4 538 → 4 528 |

Парная медиана TCP/443 составляет +16,2% по пропускной способности, −15,0% по CPU и −14,5% по CPU на пакет из очереди. Диапазоны пар составили −13,3…+32,0% по скорости и −26,6…+12,0% по CPU. Число пакетов в очереди менялось по парам в пределах −1,25…+0,22%. Для TCP/445 парная медиана −4,1%, диапазон −23,0…+18,7%. Устойчивый сдвиг скорости вне NFQUEUE не подтверждён. Версия только с переиспользованием поиска в первой серии повысила парную медиану CPU на 8,1%, поэтому в кандидат вошёл вариант с очисткой по сроку.

Размер x86-64 musl `r2o-datapath` изменился с 1 726 368 до 1 726 720 байт (+352). MIPS32r2 little-endian soft-float изменился с 2 050 920 до 2 051 816 байт (+896).

## Подбор и полноценный ответ LAN

В каждой ячейке указаны секунды от первого запроса к цели до подтверждения плана, полного LAN-ответа и видимости привязки в файле каталога соответственно. Прикладная проверка требует проверенный сертификат, HTTP 200 и ожидаемое тело. Второй сценарий направлен на `b.example.net` и `198.51.100.6` при уже сохранённом результате для `a.example.com` и `198.51.100.2`. Первый запрос ко второй цели тоже должен не получить полный ответ. Поиск проверяется по новой привязке и отдельной записи о подтверждении в контроллере.

## RSS после прогрева

Суммарный RSS datapath и controller на OpenWrt с baseline составил 9 492 КиБ в первом замере, 10 448 КиБ на 603-й секунде и 11 264 КиБ на 1 206-й. Из 816 КиБ роста во второй половине 580 КиБ пришлось на controller и 236 КиБ на datapath. Последние два замера совпали, а предшествующие продолжали расти. Стабилизация на длительном интервале не подтверждена.

В отдельном запуске того же baseline после прогрева без дальнейших запросов RSS вырос с 9 484 до 9 700 КиБ за 301 с. Всё изменение попало в `RssAnon`. `RssFile` обоих процессов не изменился. Наблюдения показывают рост резидентной анонимной памяти даже без клиентской нагрузки. Эти измерения не определяют причину роста и не подтверждают утечку.

В сопоставимом 603-секундном прогоне итоговый кандидат вырос с 9 492 до 10 108 КиБ против 10 448 КиБ у baseline на той же отметке. На последнем 30-секундном интервале кандидат добавил 20 КиБ. Все 126 ответов дошли до LAN-клиента без потерь NFQUEUE. PID не менялись и дескрипторы не накапливались. Удаление восстановило исходные настройки гостя.
