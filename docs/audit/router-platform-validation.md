# Приёмка платформы Keenetic и OpenWrt

Базовый коммит `af6e8b156bf3cc4615e4764d2cc553ff7476d79f`. Управление firewall и DNS выполняет `r2o-datapath`. Один поток согласования обслуживает обе очереди и получает события по имеющемуся rtnetlink, системным hooks и таймеру `HEAL_EVERY`. Входы init и контроллера сохранены.

## Поведение

| Пункты аудита | Реализация и проверка |
| --- | --- |
| F1, F1a | Проверяются порядок переходов, содержимое принадлежащих R2O цепочек, IPv4 UDP MASQUERADE, peer NFQUEUE и режим COPY_PACKET. CLI выводит sequence и счётчики потерь. Стенд вставляет ранний RETURN и удаляет NAT. После обнаружения и согласования свежие соединения снова дают события очереди. Статус отдельно помечает покрытие LAN как непроверенное. |
| F2 | `nf_conntrack_acct` проверяется с чтением после записи. Ядро создаёт счётчики для новых записей. Старые записи без расширения остаются ограничены до завершения своей сессии. В VM fresh TCP при accounting=0 даёт нулевой прирост очереди, после события и восстановления accounting следующая сессия видна. |
| F3–F5 | Новые потоки, которые может захватывать NFQUEUE, получают окно видимости в admission fw4 или в правилах PPE, если Keenetic предоставляет цель. OpenWrt возвращает длинные потоки в flowtable. Устаревшие глобальные настройки восстанавливаются из журнала. Ошибка записи, commit, reload или проверки оставляет журнал пригодным для повтора. Селективность и взаимодействие PPE с FastNAT требуют проверки на железе. |
| F6 | Временные DNS-привязки записываются с идентификатором загрузки и монотонным сроком. Атомарный пакет nft включает действующие элементы. Для iptables используются ipset и транзакции по таблицам, включая точный `hash:net` на старых ABI. Восстановление округляет остаток TTL вниз. |
| F7 | Привязка по UID требует nft и подтверждения настройки NFQA_CFG_F_UID_GID для текущего queue peer. Пакетная проверка владельца сохраняется в datapath. Стенд QEMU проверяет установку и TTL UID-привязки на nft. Полный DoH3-запрос с реальным resolver остаётся отдельной полевой проверкой. |
| F8 | Каталог хранит источник подтверждения в `verified_by`. Журнал автоподбора различает локальный зонд, TLS-рукопожатие, повтор ClientHello и событие клиентского потока. Прикладной результат LAN подтверждается отдельным клиентским тестом. |
| F9 | Равенство маршрутов локального зонда, raw-посылки и транзита при произвольном RPDB не подтверждено. Маршрут по `iif` может отличаться даже при одинаковых назначении и mark. |
| F10 | События смены маршрута, правил, линка и адресов инвалидируют PMTU raw-сокета через существующий rtnetlink. Изменение маршрута к префиксу инвалидирует PMTU без перестройки firewall. |
| F11 | На ядрах без `MemAvailable` оценка использует `MemFree` и часть освобождаемого кэша. Давление CPU, conntrack и NFQUEUE уменьшает предел при наличии соответствующих измерений. |
| F12 | При отказе локального резолвера bootstrap пробует числовые обычные глобальные DNS из NDM. Ошибка чтения NDM оставляет предыдущие исключения, а отказ резолвинга сохраняет адрес той же пары hostname/port. Для холодного старта без доступного обычного DNS или bootstrap-адреса независимое восстановление не доказано. |

Окно входа в flowtable действует с пустым `R2O_SOFTWARE_PATH_ENDPOINTS`. Для точного IP, протокола и порта эта настройка задаёт дополнительное исключение. Пример для контролируемого origin:

```sh
R2O_SOFTWARE_PATH_ENDPOINTS='tcp://192.0.2.10:443 udp://[2001:db8::10]:443'
```

Существующие ускоренные соединения сохраняют состояние до завершения. После пересборки fw4 есть интервал до обработки события согласования. На Keenetic статус показывает наличие PPE, установку правил и состояние FastNAT. На OpenWrt `fw4_admission=bounded` подтверждает состояние правила и цепочки R2O, `lan_coverage=unverified` относится к проверке трафика. За пределами окна обход netfilter возможен. HTTP на портах `HTTP_KEEPALIVE_PORTS` сохраняет видимость последующих запросов.

## Стенды и нагрузка

- Linux 3.4.113 x86-64 из архива Ubuntu Mainline, userspace LEDE 17.01.7 и iptables 1.4.21. Трафик loopback на тестовом адресе, с реальным Netfilter.
- Linux 4.4.182 x86-64 из LEDE 17.01.7, iptables 1.4.21. Повтор сценариев legacy, loopback.
- Linux 6.12.94 x86-64 из OpenWrt 25.12.5, nftables 1.1.6. Реальный программный транзит между LAN и WAN через две пары veth. Admission в стенде повторяет стандартное выражение fw4.
- Сборки MIPS32 little-endian и ARMv5 musl собраны штатным набором флагов R2O. Двоичный файл x86-64 также собран статически с musl. Зависимости workspace сохранены.

Для парных замеров использованы QEMU TCG, 2 vCPU, 256 МиБ, режим observe, 64 слота для потоков и одинаковая нагрузка без ускорения в обоих вариантах. Одна выборка содержит 400 TCP-передач по 1 МиБ после отдельного прогрева. В таблице медианы трёх выборок и CPU user+system datapath. Значения throughput на loopback и veth описывают соответствующий стенд.

На 6.12.94 две LAN-загрузки по 4 МиБ прошли с сохранением содержимого. Для выбранного TCP/443 получено 54 события NFQUEUE, для соседнего TCP/445 с flowtable — 8. Проверены восстановление после события rtnetlink, откат правила admission и привязка очереди IPv6. На 3.4.113 с выгруженным `ip_set_hash_ipport` подтверждён точный fallback `hash:net`. Отдельно прошли восстановление по изменению адреса, новый IPv4-трафик после исправления accounting и привязка IPv6.

## Проведение регрессий

`scripts/test-router-firewall.sh` проверяет nftables, ранний RETURN, событие согласования и отключение peer в отдельном сетевом пространстве. `scripts/test-router-dns-route-netns.sh` проверяет IPv4 и IPv6 DNS-привязки. Для ошибок восстановления используются `scripts/test-router-platform-rollback.sh` и `scripts/test-router-ppe-deoffload.sh`. Живые стенды дополнительно удаляют NAT и DNS-таблицу, меняют accounting и сопоставляют обе стороны передачи со счётчиком NFQUEUE.

На хосте тесты datapath дали 444 успешных результата, 23 пропуска и те же 20 отказов EPERM, которые воспроизводятся на базовом коммите. Изолированные прогоны QEMU используют права гостевого ядра. Проверка workspace и кросс-сборки проводились локально.

## Повторная проверка с пустым списком endpoints

Сравнение новой серии выполнено с `main` на `7a63834`. `scripts/test-router-flowtable-netns.sh` открывает настоящий NFQUEUE в `apply` и передаёт пакеты через гостевой OpenWrt 25.12.5, Linux 6.12.94. Клиент и origin находятся в разных netns. Контрольный счётчик расположен непосредственно перед postrouting NFQUEUE. В обеих сборках клиент получил полные данные. Изменилось окно видимости пакетов.

| --- | ---: | ---: |
| TCP IPv4, передача 4 МиБ | 13 пакетов | 45 пакетов |

В этой выборке меньше 2% данных TCP прошло через postrouting у кандидата. Оставшийся объём прошёл через flowtable. Восстановление admission после пересборки fw4 проверено вместе со стабильностью handles при повторном применении. Статус обнаруживает исчезновение защиты при наличии работающего слушателя NFQUEUE.

В худшей паре финальная версия уступила `7a63834` на 10,3%.

Профиль `/proc` показал нагрузку в основном потоке. На отдельном прогоне `strace -c` при примерно 690 событиях очереди выявил 695 безрезультатных `accept4` для сокета снимков. После его включения в существующий `poll` пустые `accept4` исчезли. Получение приветствия на канале снимков проверено с работающим datapath.

Полный `apply` из пустого каталога подтвердил сохранение STUN-привязки и клиентский ответ на IPv4/IPv6. От первых запросов до сохранения в локальном сценарии заняло 5,88 → 5,97 с для IPv4 и 5,96 → 5,84 с для IPv6. В отдельном сценарии Discord Discovery клиент получил ответ, а после перезапуска вновь применился сохранённый план. В TLS-стенде с локальным origin обе сборки автоматически сохранили план и затем получили HTTP 200 по HTTPS. Проверки QUIC Initial, локального HTTP/3 DNS и DoQ прошли независимо. QUIC-сценарий с пустым каталогом на loopback проверяет запуск подбора, после чего контроллер отклоняет loopback как цель.

## Физическая приёмка

На Viva KN-1910 и Hopper KN-3810 нужны парные LAN/WAN-трассы и счётчики PPE/FastNAT. По отдельности проверить Ethernet, Wi-Fi, IPoE и PPPoE, IPv4 и IPv6, начало и поздние фазы TCP/QUIC, существующие fast-path bindings и обычный трафик рядом с выбранным. Отдельно воспроизвести дубликаты и порядок NDM hooks, потерю upstream DNS и UID фактического DoH3 resolver. Для сопоставимых CPU, PSS и пропускной способности на физическом роутере нужен одинаковый набор потоков до и после.

Транзитный `apply` с реальными Rutor, X, YouTube и Discord, переключение физического WAN и полный автоматический подбор QUIC в LAN остаются непроверенными. Гостевые результаты подтверждают программный тракт, восстановление правил и локальные протокольные сценарии. Эквивалентность маршрутов F9 и падение throughput на стенде OpenWrt остаются блокерами приёмки.
