# Физическая проверка PPE и FastNAT

Проверять Viva KN-1910 и Hopper KN-3810 отдельно. Зафиксировать полную версию KeeneticOS, версию кандидата, тип WAN, MTU, включённые IPv4/IPv6, модель LAN-клиента и тип подключения.

Сценарий [diagnose-keenetic-offload.sh](../../scripts/diagnose-keenetic-offload.sh) снимает состояние от root. Он читает sysctl, журнал восстановления, счётчики правил и очередей. В качестве дополнительных аргументов можно указать имена WAN и LAN интерфейсов. Обычный запуск использует активную установку. Для прямого запуска локального datapath задайте `R2O_DATAPATH_BIN`, `R2O_DIR` и действующие параметры платформы.

```sh
MODEL=KN-1910 # На Hopper укажите KN-3810.
sh diagnose-keenetic-offload.sh "$MODEL" before > before.txt
# Запустите контролируемые передачи с LAN.
sh diagnose-keenetic-offload.sh "$MODEL" running > running.txt
# После штатного пересоздания WAN/NDM запустите новые клиентские соединения.
sh diagnose-keenetic-offload.sh "$MODEL" after-ndm > after-ndm.txt
```

## F3. Видимость активного потока

1. Поднимите контролируемый origin за WAN с HTTPS/TCP и HTTP/3/UDP. На LAN проверьте сертификат, код ответа и хеш скачанного файла. Используйте тот же origin для контрольного TCP-порта за пределами настроенного окна захвата.
2. Запустите передачу до старта кандидата. После старта проверьте ту же сессию и новые соединения с новыми исходными портами. Список `R2O_SOFTWARE_PATH_ENDPOINTS` оставьте пустым. Для каждого запроса сопоставьте адреса, порты и время с LAN/WAN-трассами, разницами счётчиков PPE и NFQUEUE и наблюдением ClientHello.
3. Проверьте начало и длинное тело TCP, первые и последующие запросы HTTP keep-alive, QUIC Initial и HTTP/3. Для свежего контролируемого потока требуются видимое начало соединения и полный ответ приложения. Для обычного потока подтвердите сохранение ускорения и сравните полезную скорость, CPU, память и потери с исходной сборкой.
4. Повторите по IPv4/IPv6, Ethernet/Wi-Fi и IPoE/PPPoE, если эти режимы доступны на маршрутизаторе. Снимите данные до и после пересборки firewall и переподключения WAN. Укажите отдельно ранее ускоренные соединения и новые. Если драйвер показывает аппаратные счётчики, приложите дельты вместе с трассами.

`PPE: target=present` и `ipv4_rules=installed` подтверждают состояние конфигурации. Для доказательства покрытия нужен сопоставленный поток. При `unavailable` укажите модель, версию прошивки и отсутствующий интерфейс ядра.

## F4. Состояние FastNAT

1. Снимите значения до запуска, после запуска, после штатного переподключения WAN/события NDM и после остановки кандидата. Сравните `nf_conntrack_fastnat` и наличие `fastnat_journal`. Снимки должны относиться к одной загрузке.
2. Повторите проверку с работающим цельным обычным потоком и свежим HTTP/3. Успех требует сохранения штатного значения FastNAT, целостности обычной передачи и видимости нужной фазы свежего потока.
3. При переходе со старого выпуска, оставившего `fastnat.saved`, проверьте восстановление значения и снятие записи после подтверждённого чтения. Для значения, изменённого извне, ожидайте сохранение журнала и диагностику. Сценарий со специально изменённым sysctl проверяется на симулированной файловой системе QEMU.

## Границы QEMU

Профили с лимитами памяти 128 и 256 МиБ используют обычный Linux 3.4.113 и 4.4.182. Они проверяют iptables, NFQUEUE, обработку сетевого события, read-back учёта, состояние при отсутствии vendor target и логику журнала на моделируемом sysctl. Стенд NDM использует воспроизводимые ответы CLI. Дополнительный QEMU Malta с Linux 6.1.176 проверяет живой LAN/WAN-транзит статического MIPS32r2 приложения. MT7621AT, EN7528DU, драйверы KeeneticOS, аппаратные bindings, Wi-Fi и физический WAN проверяются на устройствах.
