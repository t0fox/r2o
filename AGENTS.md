# D2O → R2O — Agent Instructions

## Mission

Последовательно перенести всю функциональность D2O с C на Rust (R2O), добившись **100% доказанного функционального паритета**.

Главный источник прогресса — `functional-parity-matrix.md`. Используй установленный скилл `.agents/skills/migrate-to-rust` как методику миграции.

**Приоритет: корректность и функциональный паритет > производительность > чистота реализации.**

## Migration Rules

0. **Telegram-прокси.** Реализацию Telegram runtime (`crates/r2o-telegram`) брать полностью из донора z2kOW (`tg-proxy`). C11 D2O Telegram — только oracle для differential-проверок, не источник переноса. Не заменять z2kOW-код самописным C-портом.
1. Перед изменениями изучай актуальные исходники C, Rust, зависимости и матрицу паритета.
2. Продолжай существующую архитектуру R2O. Не переписывай уже работающие подсистемы без доказанной необходимости.
3. Переноси полную функциональность: алгоритмы, состояния, обработку ошибок, таймауты, протоколы и побочные эффекты.
4. Сохраняй совместимость ABI, Linux API, OpenWrt/musl, сетевого datapath и поддерживаемых архитектур.
5. Запрещены заглушки, имитации функциональности и упрощения, нарушающие поведение D2O.
6. Safe Rust предпочтителен, но не обязателен любой ценой. Обоснованный `unsafe` допустим для FFI, системных вызовов и низкоуровневых операций.
7. Не выполняй SIMD/PGO-оптимизации, если они мешают переносу, совместимости или проверке паритета.
8. Не удаляй C-реализацию, пока эквивалентность её замены не подтверждена.

## Functional Parity

Каждый закрываемый пункт матрицы должен иметь проверяемые доказательства:

- Реальная Rust-реализация соответствующей функциональности.
- Unit/integration-тесты для нормальных и ошибочных сценариев.
- C/Rust differential-тесты, где доступен C-oracle.
- Проверка совместимости и регрессий.
- Фактические результаты выполненных команд.

**Компиляция, успешный mock-тест или наличие похожей функции не доказывают функциональный паритет.**

Не отмечай пункты как полностью эквивалентные при непроверенных production-, аппаратных или timing-сценариях. Явно фиксируй ограничения проверок.

## Testing

После каждого логического изменения запускай релевантные проверки. По мере необходимости используй:

- `cargo fmt --check`
- `cargo check --workspace --all-targets`
- `cargo test` для затронутых crates
- Существующие differential/integration shell-тесты
- OpenWrt/musl cross-build и платформенные тесты

Проверяй память, конкурентность, таймауты, восстановление после ошибок и сетевое поведение.

Не утверждай, что тест выполнен, если он не запускался. Не подменяй отсутствующее оборудование симуляцией без указания ограничений.

## Autonomous Workflow

1. Проверяй состояние Git, актуальные инструкции проекта и матрицу.
2. Выбирай следующий незакрытый пункт, который реально можно продвинуть.
3. Анализируй C-реализацию и существующий Rust-код.
4. Реализуй перенос и добавляй тесты.
5. Исправляй обнаруженные регрессии.
6. Обновляй матрицу только после подтверждения результата.
7. Создавай небольшие осмысленные коммиты.
8. Продолжай со следующим независимым пунктом.

Не останавливайся после анализа или одного успешного изменения, если остаётся доступная работа.

Если задача требует недоступного оборудования, сети или production-oracle, зафиксируй блокировку и переходи к следующей выполнимой задаче.

## Safety and Git

- Работай в отдельной ветке.
- Не перезаписывай чужие незакоммиченные изменения.
- Не удаляй тесты ради успешного CI.
- Не изменяй рабочие роутеры без разрешения.
- Не выполняй merge, push или release без явного запроса.
- Не объявляй 100% готовности без подтверждения всех пунктов матрицы.

## Reporting

По завершении рабочего этапа кратко сообщай:

- Перенесённые подсистемы и коммиты.
- Реально выполненные тесты и результаты.
- Закрытые и частичные пункты матрицы.
- Текущий подтверждённый процент паритета.
- Оставшиеся проблемы и следующие задачи.

**Главное правило: никакого фиктивного прогресса. Только работающая Rust-реализация и воспроизводимые доказательства.**
